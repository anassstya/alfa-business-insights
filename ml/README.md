# ML для персонализированной новостной аналитики

Цель первого ML-MVP: получить базовый профиль, выполнить веб-исследование, объяснить возможное влияние событий с учётом роли пользователя и передать результат бэкенду. PDF-аналитика Альфа-Банка подключается после первых работающих веб-инсайтов.

Подготовлен план реализации от прототипа без Judge до проверки качества и последующего улучшения поиска. Контракты, загрузчик профиля и первый fixture pipeline реализованы.

## Текущее состояние: итерация 3 — карта факторов

Добавлен детерминированный `build_exposures(profile, role, goal)` в
`src/exposures.py`: правила v1 по продуктам, ФТС, отрасли, региону, труду,
группе и концентрации входящих/исходящих платежей. Каждый фактор содержит
`rule_id`, пути исходных признаков, наблюдаемые значения, темы поиска,
оговорки и ссылку на строку матрицы или раздел плана. Пороги платежей
строго `>0.30` и `>0.50` в `CONCENTRATION_THRESHOLDS`. Роль меняет приоритет,
не факты; `goal` остаётся данными. Масштаб, возраст и стадия — небольшие
модификаторы очередности, `client_type` сам по себе не создаёт новостной фактор.
Подробные правила для реально встречающихся кодов сверены с локальным JSON.
Правило для ювелирного производства (`32.12`) оставлено для различения
механизма с добычей золота, хотя этот код в текущем снимке не найден.

Fixture pipeline кладёт карту в `research_context.exposures` и помечает
веб-покрытие как не начатое. Демонстрационный инсайт остаётся гипотетическим.
Ролевые профили и runtime инструкция находятся в [prompts/](prompts/).
Поиск и запись в Supabase на этом шаге не выполняются.

```powershell
$env:ML_FIXTURE_MODE = 'true'
python -m ml.src.analyze_cli ml/docs/fixture_request.json
python -m unittest discover -s ml/tests -v
```

Следующий шаг — **промпт 4** из [docs/CODEX_PROMPTS.md](docs/CODEX_PROMPTS.md).

## Предыдущий этап: итерация 2 — fixture milestone

Реализованы предложенные типизированные контракты v1 и read-only загрузчик
`get_company_profile(company_id)` для локального JSON и Supabase. Схемы и
компактные примеры: [docs/contracts/](docs/contracts/). Fixture pipeline даёт
демонстрационный `AnalysisResult` через CLI и внутренний `POST /internal/analyze`;
`GET /health` проверяет процесс. Это гипотетические evidence и инсайт без поиска,
LLM, PDF банка и записи в БД. Результат помечен `mode=fixture`; `analysis_jobs`
остаётся зоной ответственности бэкенда. Запуск, авторизация и примеры контракта:
[docs/FIXTURE_SERVICE.md](docs/FIXTURE_SERVICE.md).

Для Python 3.12: `python -m pip install -r ml/requirements.txt`. Только для
отдельной пакетной подготовки с `base_context.py` нужен
`ml/requirements-batch.txt` (включает pandas). Файл `ml/.env.example` перечисляет
параметры подключения без секретов. Рабочие значения берутся из окружения или
существующего корневого `.env`; обязательны явные удалённые host, port и
`POSTGRES_CONNECTION_MODE=direct|session|transaction`. Для transaction pooler
prepared statements отключены. Локальный Postgres не требуется.

```powershell
python -m ml.src.profile_cli U_1 --source json
python -m ml.src.profile_cli U_1 --source supabase
python -m unittest discover -s ml/tests -v
```

Полный JSON явно загружается один раз при создании offline-адаптера. Локальный
`companies.csv` не содержит числового `companies.id`, поэтому offline CLI не
проверяет пару ID; production-адаптер проверяет её по `companies`. Для live
чтения требуется заданный `POSTGRES_CONNECTION_MODE`; без него проверка
Supabase в предыдущей итерации не выполнялась.

Итерации 1–3 реализованы; продолжать с промпта 4. После промпта 6 — полный веб-проход без Judge с сохранением расширенного контекста. Промпт 7 добавляет PDF-аналитику Альфа-Банка как отключаемое расширение. Промпты 8–10 готовят демонстрацию, 11–12 — дальнейшие улучшения.

Актуальное веб-исследование хранится в `company_contexts.payload.web_research`, позднее банковское — в `payload.alfa_analytics`. При обновлении соответствующий блок заменяется целиком с сохранением базовой информации. `analysis_jobs.result` хранит инсайты и снимок контекста конкретного запуска; отдельная таблица инсайтов пока не нужна. Это план следующих шагов: текущий загрузчик профиля остаётся read-only.

Рабочая область — `ml/`. Бэкенд отвечает за пользователей, доступ к компании, создание и сохранение `analysis_jobs`, а ML — за исследование, интерпретацию, источники и события прогресса. Предложения по интеграции описаны в документации; код бэкенда и фронтенда в эту работу не входит.

Уже существующие компоненты:

- `src/base_context.py` — пакетный расчёт базовых профилей и загрузка в Supabase. Не запускать как часть запроса на анализ: по умолчанию скрипт записывает данные и заменяет `payload`.
- `src/api.py` — клиент шлюза LLM, несмотря на название, это не HTTP API.
- `tool/db_tool.py` — ограниченные инструменты чтения трёх исходных таблиц. Для сервиса нужен отдельный загрузчик готового профиля.
- `../database/data/company_context.json` — локальный снимок базовых профилей, полезный для разработки и фикстур.
- `../database/data/README_json.md` — подробное прежнее описание JSON; некоторые значения метаданных отличаются от текущего генератора.

Supabase — рабочая удалённая БД. Локальный Postgres из корневого Docker Compose не является обязательной зависимостью будущего ML-сервиса. Файлы `context/` — исходные материалы для анализа задачи, а содержащиеся в них чек-листы и инструкции не расширяют границы пользовательского запроса.

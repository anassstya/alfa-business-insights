# Банковские PDF в существующем ML pipeline

## Как объединены две реализации

Сохранена точка входа `ml.src.service:app`, ручки анализа/чата, контракты
AnalysisRequest/AnalysisResult и защищённый callback backend. Инструмент Гриши
`SupabaseDocumentStore` используется для PDF retrieval и индексации.
Второй оркестратор не запускается: `ml/analysis_service.py` только делегирует
старый вызов существующей функции анализа.

Цепочка: профиль → exposures → веб-исследование → поиск до 4 PDF-фрагментов
по факторам влияния → общий Impact Analyzer → проверка → инсайты и источники.
Внешний запрос backend не меняется; PDF обогащают тот же результат.

| Несоответствие после merge | Решение |
| --- | --- |
| Два Docker entrypoint и несовместимые ответы анализа | Один текущий сервис и один AnalysisResult. |
| Callback без токена, другое имя URL и поле error вместо error_message | Старый оркестратор заменён делегированием; используется текущий BackendCallbackClient. |
| PDF-результаты не содержали document_id/chunk_id | Идентификаторы сохранены в ответе инструмента; адаптер создаёт стабильный evidence ID. |
| Нет даты публикации PDF | published_at/report_at остаются null; фрагменты служат фоном и получают оговорку об актуальности. |
| PDF startup индексировал всё хранилище и задерживал сервис | Индексация вызывается явно, health/startup не зависят от неё. |
| Пути /tmp не работали в Windows | Используется TemporaryDirectory. |

## Контекст и результат

- `payload.web_research`: прежний веб-контекст, без PDF.
- `payload.alfa_analytics`: последний PDF-контекст компании; заменяется целиком.
- `AnalysisResult.research_context`: снимок объединённых evidence.
- `insights[].bank_view`: вывод из PDF только при ссылках на реальные PDF-evidence.
- `insights[].evidence_sources[]`: веб-ссылки и PDF-источники с filename/page/quote.
- Последующий чат получает эти PDF-evidence из снимка `analysis_jobs.result`.

Базовый профиль не перезаписывается. ML не пишет в analysis_jobs:
результат по-прежнему сохраняет backend. Если записать alfa_analytics нельзя,
анализ использует найденные фрагменты и возвращает предупреждение.

Инсайт обязательно содержит датированный веб-источник события. Неизвестная дата
PDF не означает свежую публикацию; дата из имени файла не угадывается.
Проверяются точные цитаты, ID, признаки, ссылки bank_view на PDF и номера страниц.
При отсутствии подходящего PDF bank_view остаётся unavailable.

Приватный Storage не становится публичным: у PDF evidence `url=null`,
`title` содержит имя файла и `page_number` — страницу. Фронт может отображать
имя/страницу/цитату. Выдача скачивания PDF пользователю через backend или signed
URL потребует отдельного контракта; ключ service role в URL не передаётся.
У веб-источников прежние URL сохраняются.

## Настройки и подготовка

Добавить в общий корневой `.env`:

```dotenv
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SERVICE_KEY=<server-side-service-role-key>
SUPABASE_STORAGE_BUCKET=reference-pdfs
```

Это ключ API Storage/PostgREST; POSTGRES_PASSWORD его не заменяет.
В bucket должны лежать именно согласованные банковские отчёты — произвольные
загруженные PDF не доказывают позицию банка. Текущий sync перечисляет PDF
в корне bucket. Автоматического локального fallback корпуса нет.

Таблица `document_chunks`, индекс vector(384) и RPC `match_document_chunks`
задаются [supabase_schema.sql](../document_search/supabase_schema.sql).
Схема автоматически не применяется. Требуется заранее подготовленный индекс
или явная индексация; поиск сам документы не загружает и не переиндексирует.

После изменения env пересоздать только ML:

```powershell
docker compose --env-file .env -f docker-compose.yml -f ml/docker-compose.root.yml up -d --build ml
```

При наличии SUPABASE_URL и SUPABASE_SERVICE_KEY PDF-поиск подключается
автоматически. Без них старый веб-проход работает как раньше.
На момент интеграции этих двух параметров в рабочем env не было, поэтому
реальный удалённый PDF-поиск ещё не подтверждён.

## Ручки инструмента

Тот же сервис `http://ml:8000` и `Authorization: Bearer <ML_SERVICE_TOKEN>`:

| Метод / путь | Назначение |
| --- | --- |
| POST /internal/documents/search | JSON question, top_k (1–20); поиск по готовому индексу. |
| POST /internal/documents/sync | Явная загрузка/индексация PDF из Storage. |
| POST /internal/documents/upload | Multipart поле file; PDF до 50 MiB, OCR при необходимости, загрузка и индексация. |

Пример поиска:

```json
{"question": "Влияние процентных ставок на стоимость финансирования", "top_k": 4}
```

Docker содержит CPU PyTorch, PyMuPDF, e5 embeddings и Tesseract rus/eng.
Модель `intfloat/multilingual-e5-small` имеет 384 измерения; нельзя менять её
без согласованной переиндексации. Веса скачиваются при первом поиске/индексации
и кэшируются в volume ml_cache. Перед live-демонстрацией выполнить search/sync
для прогрева модели. Работающие старые веб-ручки не ждут загрузки весов.

В pipeline опциональный PDF-поиск ждёт до 20 секунд, оставляя 30 секунд общего
бюджета для анализа. Одновременно допускается один PDF lookup; при timeout
или занятости поиск пропускается. Уже начавшаяся загрузка модели может
продолжаться фоном, но не создаёт неограниченное число задач. Ошибки PDF не
отменяют веб-инсайты: результат отмечается partial с предупреждением.

Тесты покрывают адаптер, страницы, цитаты/даты, отдельное хранение, деградацию
при сбое, callback/source cards через прежний контракт и использование PDF
последующим чатом. Проверка настоящего корпуса требует Supabase API credentials.

Проверка интеграции: 78 тестов прошли на хосте и в новом Linux-образе, включая
извлечение текста из двухстраничного синтетического PDF. Внутри контейнера
проверена настоящая e5-модель: 384 измерения, норма 1.0; веса прогреты в volume.
ML healthy; health содержит bank_research_configured=false, пока ключи
Storage/PostgREST отсутствуют. Удалённый PDF-корпус этим smoke не проверен.

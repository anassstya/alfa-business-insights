# ML-чат по сохранённому анализу

## Назначение

Чат отвечает на уточнения по одной завершённой сессии `analysis_jobs.id`.
ML сам читает `analysis_jobs.result` из Supabase: инсайты, роль, цель, снимок
профиля и evidence. История вопросов/ответов приходит от backend в запросе.
Новый веб-поиск и повторное скачивание сайтов не выполняются: используются
сохранённые фрагменты источников. При недостатке данных ответ обозначает ограничение.
ML не пишет в `analysis_jobs` или `chat_messages`.

## Вызов из backend

`POST http://ml:8000/internal/chat` в общей Docker-сети.
С хоста — `http://127.0.0.1:8001/internal/chat` после обновления контейнера.
Заголовки: `Authorization: Bearer <ML_SERVICE_TOKEN>` и
`Content-Type: application/json`. Callback для чата не используется;
ответ возвращается обычным HTTP JSON.

```json
{
  "job_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "history": [
    {"role": "user", "content": "Что означает первый инсайт?"},
    {"role": "assistant", "content": "Он описывает возможное влияние условий финансирования."}
  ],
  "message": "А почему это важно для моей роли?"
}
```

`job_id` и `message` обязательны. `history` можно опустить или передать `[]`.
История идёт от старых сообщений к новым, только из этой сессии; текущий вопрос
передаётся отдельно в `message`, без дублирования в `history`.
Роли истории: `user` и `assistant`. Допускаются необязательные `id` (UUID) и
`created_at` (ISO-дата с часовым поясом), как в существующей модели backend.
Роль пользователя и цель анализа берутся из сохранённого результата.

Лимиты: вопрос — 4000 символов; история — до 12 сообщений по 8000 символов;
суммарный сериализованный контекст модели — до 65 000 символов. При превышении
передавать последние сообщения, сохраняя порядок; ML не обрезает контекст молча.
Рекомендуемый timeout HTTP-клиента — 150 секунд: бюджет модели до 120 секунд,
плюс время чтения Supabase. Это синхронный ответ без потоковой генерации.

## Ответ

Пример формы; текст и ID здесь иллюстративные:

```json
{
  "job_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "answer": "Для вашей роли важен риск изменения стоимости финансирования. Это гипотеза из сохранённого анализа, требующая проверки условий договора.",
  "insight_refs": ["insight-1"],
  "evidence_refs": ["evidence-1"],
  "sources": [
    {
      "evidence_id": "evidence-1",
      "title": "Название сохранённого материала",
      "url": "https://example.org/material",
      "publisher": "Издатель",
      "published_at": null,
      "page_number": null,
      "quote": "Фрагмент материала из сохранённого evidence."
    }
  ],
  "insufficient_context": false,
  "mode": "saved_analysis"
}
```

`sources` собирает код из сохранённых evidence, а не из URL, сгенерированных
моделью. Неизвестные ID инсайтов/источников отклоняются. URL и даты могут быть
null. `insufficient_context=true` — штатный ответ с ограничением данных,
а не техническая ошибка. История не считается доказательством фактов.

Схемы: [ChatRequest](contracts/ChatRequest.schema.json),
[ChatResponse](contracts/ChatResponse.schema.json).
Python-функция: `answer_analysis_question(job_id, message, history=[...])`
в `ml.src.analysis_chat`.

## Как подключить к существующему backend

На проверенной версии backend уже есть:

- `GET /api/v1/analysis/jobs/{jobID}/chat/messages` — читает `chat_messages`.
- `POST /api/v1/analysis/jobs/{jobID}/chat/messages` — сохраняет сообщение
  пользователя и возвращает `message_id`; ML пока не вызывает.
- `GET /api/v1/analysis/jobs/{jobID}/chat/events` — пока возвращает 503.
- `backend/mlclient/client.go` — умеет вызывать анализ, метода чата ещё нет.

Рекомендуемая последовательность для владельца backend:

1. Проверить право пользователя на сессию и её завершённость.
2. Сохранить вопрос и запомнить его `message_id`.
3. В обработчике этой сессии собрать последние 12 предшествующих сообщений
   из `chat_messages`, исключив текущий вопрос. Передать `role`, `content`
   и, при необходимости, `id`, `created_at` в `history`.
4. Вызвать `/internal/chat`: `job_id`, `history`, текущий вопрос в `message`.
5. Сохранить полученный `answer` как `role=assistant` в той же сессии.
6. Отдать ответ и `sources` фронтенду. Если нужен асинхронный frontend API,
   backend сам уведомляет через SSE или предоставляет polling.

Существующая модель `ChatMessage` хранит только `id`, `role`, `content`,
`created_at`. Чтобы источники сохранялись после перезагрузки диалога, владельцу
backend нужно решить, где хранить metadata ответа (`sources`, refs и признак
недостатка данных). В ML эти поля уже возвращаются отдельными JSON-полями.

ML stateless: повтор одного запроса может повторно вызвать модель.
Идемпотентность по `message_id`, последовательная обработка вопросов одной
сессии и запись ответа ровно один раз относятся к backend. При ошибке ML
не сохранять текст ошибки как якобы ответ аналитика.
Ни один файл backend в рамках этой задачи не изменялся.

## Ошибки HTTP

| Код | Значение |
| --- | --- |
| 401 | Нет/неверный сервисный Bearer-токен. |
| 404 | Сессия отсутствует или не видна через RLS. |
| 409 | Анализ ещё не завершён, результат отсутствует/повреждён либо изменился при чтении. |
| 413 | Результат или контекст слишком большой. |
| 422 | Неверный UUID, пустой/слишком длинный вопрос, неверная история. |
| 502 | Модель вернула неверный формат или ссылки на неизвестные ID. |
| 503 | Недоступны хранилище/модель, нет SELECT или исчерпан бюджет модели. |

Ошибка содержит `detail.code`. `history` из другой сессии ML определить не
может: backend обязан формировать её по переданному `job_id`.

## Окружение и проверка

По умолчанию `ML_CHAT_RESULT_SOURCE=supabase`. Используются существующие
`POSTGRES_*` и `MODEL_API_KEY`. Требуется только SELECT к `analysis_jobs`.
Обновить только ML из корня репозитория:

```powershell
docker compose --env-file .env --env-file ml/docker.example -f ml/docker-compose.yml up -d --build ml
```

Резервный адаптер `ML_CHAT_RESULT_SOURCE=backend` читает существующий
`GET /api/v1/analysis/jobs/{job_id}` по адресу `ML_BACKEND_URL`; он не нужен
при прямом чтении Supabase. История и в этом режиме приходит в запросе.

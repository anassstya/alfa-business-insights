# Состояние и дальнейшие шаги ML

## Текущая архитектура

Один pipeline: профиль компании → факторы влияния → план → веб-поиск Tavily →
источники → анализ влияния с учётом роли → проверка и ранжирование → результат.
Свежий совместимый `web_research` используется повторно; при refresh заменяется
только этот блок `company_contexts.payload`.

Результат и статусы отправляются HTTP callback. Запись в `analysis_jobs.result`,
пользовательские доступы и история диалога принадлежат backend.

## Что уже есть

- Типизированные контракты, загрузка профиля из Supabase и разрешение ID компании.
- Exposure Mapper, Tavily, файловый кэш evidence, Planner и Impact Analyzer.
- Проверки формата, дат, ссылок и цитат; до пяти инсайтов с источниками.
- HTTP API и Python-функция `analyze_company(company_id, role, goal=None)`.
- Callback прогресса и результата, повторная доставка финального события.
- Отдельный Docker-сервис ML; существующий backend и корневой Compose не менялись.

Механические проверки не заменяют смысловую оценку качества. Успех fixture-тестов
не подтверждает получение качественных live-инсайтов.

## Следующие шаги

1. Создание задания и фоновый вызов ML теперь есть в backend; проверить их
   вместе с настройкой callback на развёрнутых сервисах.
2. Проверить полный live-запуск: реальная компания → инсайты → `analysis_jobs.result`
   → frontend с источниками. Проверки отдельных сервисов уже были, полный путь
   требует подтверждения.
3. ML-чат с историей и чтением `analysis_jobs.result` реализован; SELECT разрешён.
   Подключить его в backend, сохранить assistant-ответ и проверить на реальной
   завершённой сессии. [Инструкция](CHAT_INTEGRATION.md).
4. После работающих веб-инсайтов добавить первичные PDF-отчёты банка и
   `payload.alfa_analytics`. До этого `bank_view.status=unavailable` штатен.
5. На примерах оценить полезность выводов и качество поиска; затем добавлять
   дополнительный поиск при пробелах, Judge или более сложное ранжирование.
